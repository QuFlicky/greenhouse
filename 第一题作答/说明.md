# 第一题作答说明

**结论。** 一期优先消除错误的跨工位互斥，并交付可追溯、可接续的虚拟排程闭环。两个独立工位、每件 40 秒的理论上限为 180 件/小时，240 件/小时不可达。本批两工位各 120 件、全部 ready_s=0；实测首小时 180 件，全部 240 件在 4800 秒完成。建议业务确认以本批首小时 180、80 分钟清批为验收目标；若坚持首小时 240，必须另行调整硬件或工艺约束，不能在本题伪造产能。

**诊断与证据。** 修改前三个问题及初始结论保存在 `初始诊断.md`。旧代码 `ExecutionWindowPolicy.earliest` 使用全部工位的 MAX(end_s)，使本可并行的工位串行等待。`experiments.py` 的受控组只改变此窗口的工位作用域，保持输入、顺序、周期、窗口、LocalBus、Facade、存储与调用层次不变；完整实现随后与受控组逐任务核对一致。

| 虚拟指标 | 原型复跑 | 仅修正窗口 | 完整实现 |
| --- | ---: | ---: | ---: |
| 首小时完成量 | 90 | 180 | 180 |
| S1 / S2 首小时利用率 | 50% / 50% | 100% / 100% | 100% / 100% |
| 全批最后完成秒数 | 9600 | 4800 | 4800 |
| 全批平均等待秒数 | 4780 | 2380 | 2380 |

等待按 start_s−ready_s 计算。本批消除错误的跨工位等待后，剩余等待来自同工位已预留任务；相对就绪时间及本工位前一任务结束的额外延迟总计从 9560 秒降为 0。这是虚拟排程指标，不是消息处理耗时。相同消息调用链即可翻倍，支持资源约束建模为本原型的直接瓶颈；不推出真实现场不存在消息性能问题。各组均只依赖 Python 标准库与 SQLite，无服务启动步骤；基线和最终版本各用一条批量命令，接续验证额外重启两次。

**一期取舍。** ①保留唯一标识、持久受理与结果，补齐事件与事务；②暂缓六服务、消息队列和缓存，单程序分离校验、排程、存储即可；③拒绝以万条/秒消息能力承诺 240 件/小时，优先修正已验证的资源约束；④改为受控实验后选择解释；⑤暂缓三维展示、全局优化与实时大屏，先提供可查询等待、状态与统计。两人四周可分为首周诊断与目标确认、第二周闭环、第三周接入及一致性验证、第四周验收和变更缓冲；这只是计划，非交付时间保证。

**实现与接入。** 公开格式以 `../第一题材料/platform_contract.md` 为准，入口为 `backend.py` 与 `adapter.json`。批量导入和 submit 共用同一逻辑，get/report 共用 SQLite 事实源。提交在 BEGIN IMMEDIATE 内查重、找指定工位最早可容纳完整周期的空隙、写计划及 accepted/planned 事件；重试写 duplicate，合法但与批次参数不同写 conflict。锁先于排程读取，避免两个进程预留同一区间；失败回滚。查询在同一读事务中取计划、事件和指标，不写状态事件。at_s 与 ready/start/end 比较得到 not_ready、waiting、running、simulated_completed；结束边界计为模拟完成。

不变量为标识唯一、计划不改、指定工位不变、start≥ready、完整周期、同工位半开区间不相交，以及每次新计划对应一对受理/计划事件。输入严格使用 64 位范围内整数秒，拒绝布尔值、浮点、非法字段及溢出；库绑定规范化批次，拒绝换批复用。仅支持固定批次和独立工位，显式拒绝共享资源定义。单次排程扫描本工位区间，适合本批规模，不声称全局最优或任意增量订单最优。

**反例、接续和平台证据。** 同工位先提交 ready=1000、后提交 ready=0 的任务，尾时刻追加法让后者从 1040 开始；当前实现从 0 开始，且前者计划不变，见 `evidence/counterexample*.json`。这修正了“按工位取尾时刻即可处理所有请求”的简化；受控组仅用于定位原批次瓶颈。`experiment.json` 记录同库三个独立进程产生 20→240→240 个计划，逐项比较旧计划和最终计划不变；验证正常退出接续，未注入崩溃。重复事件累计 1→33→285，因为恢复重新扫描输入，最后重导 252 条全部是重试；计划始终只有 240。`platform_evidence.json` 实际通过重复、冲突、双进程并发、错误、状态边界、事件归属和指标一致性检查；`boundary_tests.txt` 另有 6 项边界测试通过。完整导出为 `evidence/result.json`，检查器原始输出为 `*_check.txt`。

**替代路线与边界。** 可按固定批次各工位就绪时间预计算确定性计划，submit 仅持久受理对应计划，优势是请求顺序不影响计划；代价是未受理任务也占预留窗口。本次选按已受理区间找空隙，以便解释当前等待且保持既有承诺。未做现场动作、鉴权、生产部署、崩溃注入或所有并发交错证明，不能推论硬件可回滚或恰好执行一次。下一步最小实验是在事务提交前后终止进程、重试相同任务，检查计划与事件原子性；若业务新增共享资源，先确认阶段约束并重新建模。关键建议“提升消息并发即可达标”被算术上限与受控实验否定，核查依据及实际 AI 使用详见根目录 `AI_USAGE.md`，本人核查仍需作答者完成。
